# Prompt file for ALIS software refactoring -- STAGE 0

> **Safety net and regression harness.** Before any refactoring begins, build an
> automated regression-test harness that runs the existing ALIS on the example
> fits and compares the output against the committed golden "reference" files.
> This harness is the safety net that gates every subsequent stage: no refactor
> change may land unless the harness still passes within the agreed tolerances.
> Stage 0 must not modify any code under `alis/`; it only adds test
> infrastructure (under `tests/`).

## Tasks

> Complete in order; log each in `ALIS/claude_prompts/logs/refactor_code_stage0_log.md`
> (date + description of work done).

**0.1 — Build the test-case inventory (manifest).**
- Discover every test case: any `.mod` file that has a sibling
  `<name>.mod.out.reference`, under both `examples/` and
  `context/fitting_examples/`. Discovery is by the *presence of the reference
  file*, not by filename pattern (the fit files are `fit_spectra*.mod`,
  `*_FINAL_MODEL.mod`, etc. — not `fit_<example>.mod`).
- For each test case record: example directory, fit `.mod` file, input data
  file(s) and their paired `<datadir>/reference_fits/<dataname>_fit.dat`, whether
  a `<name>.covar.reference` exists, whether the model uses randomness
  (`random` / `sim`, e.g. `DH/Q1243p307/…_converge_newstart76.mod`), and an
  approximate runtime.
- Handle multiple data directories: a fit may read data from several `../data*/`
  folders (e.g. `DH/J1358p6522` uses `data/` and `data_hrdx/`; `DH_orders` uses
  `datafit_orders/`), each with its own `reference_fits/`. Resolve each input
  data file's `_fit.dat` reference relative to that file's directory, not a fixed
  `data/`.
- Classify each as **fast** (the `examples/` unit tests — seconds) or **slow**
  (the `context/fitting_examples/` fits: DH, DH_orders, helium34 — minutes+).
- Exclude `prepfit`, `lsf_spline` (see plan Q21), and note the `generate`
  example as a special case (see Q0.4 below).
- Emit the manifest in a form the harness consumes (e.g. a small module-level
  list, or a generated fixture list) so the suite is data-driven.

**0.2 — Implement the pytest regression harness (under `tests/`).**
- For each test case: run `run_alis <fit>.mod` in its `model/` directory. Do
  **not** run `generate_spectra.mod` — the data already exists in `data/`.
- Compare `.mod.out` to `.mod.out.reference` by **parsing numeric fields**
  (best-fit parameters and their 1σ errors, χ², DOF) and comparing within
  tolerance; **ignore volatile header lines** (`Generated by ALIS on …`,
  `Running Time (hrs)`, `Num. of Iterations`).
- Compare the produced `<dataname>_fit.dat` model column against
  `data/reference_fits/<dataname>_fit.dat` within numeric tolerance; ignore the
  `-9.999999999e+09` sentinel rows (pixels outside `fitrange`).
- If a `<name>.covar.reference` exists, compare the emitted `.covar` within
  tolerance.
- Never overwrite a reference. Write generated outputs to a temp location (or
  clean them up after each test) so `.mod.out.reference`, `reference_fits/`, and
  `.covar.reference` remain pristine.

**0.3 — Fast/slow split and determinism.**
- Add pytest markers (e.g. `@pytest.mark.slow`) so the fast suite runs on every
  change and the slow suite runs nightly / on demand.
- Handle randomised cases: `random` converges to the same best-fit but its
  `_fit.dat` varies at the ~1e-5 level run-to-run, so it must be compared with
  the numeric tolerance (not byte-identity). Use a fixed seed wherever the
  harness can set one.

**0.4 — Tolerances.**
- **Primary gate (per subtask):** the model spectrum and χ² evaluated at a
  *fixed* parameter set (no minimisation) must reproduce the reference with χ²
  within 0.1% relative. Implement a fixed-parameter evaluation path (see Q0.1).
- **Secondary check (end-to-end):** after a full re-fit, the best-fit parameters
  must be within 10% of their 1σ error and χ² within 1%.

**0.5 — Make the harness CI-ready and documented.**
- Add pytest configuration and a short `tests/README` describing how to run the
  fast vs slow suites. (The GitHub Actions workflow itself is Stage 1.3; here we
  only ensure the harness is invokable as `pytest -m "not slow"` etc.)

## Queries

> Claude and RJC use this section to resolve ambiguities before/while executing.

**Q0.1 — Fixed-parameter evaluation.** The primary tolerance gate needs ALIS to
compute the model + χ² at a *given* parameter set without minimising. Is there a
supported way to do this in the current code (e.g. `chisq maxiter 0`, or reusing
the `generate`/`sim` machinery), or should the harness instead gate on the
end-to-end re-fit result only? Please advise the preferred mechanism.

**Response:** The current `.reference` files are generated from a full fit,
so they include the best-fit parameters and their associated χ² values. It is
possible to evaluate the model and χ² at a fixed parameter set by setting the
following parameters at the top parameter block of the `.mod` file:
`chisq miniter 0`
`chisq maxiter 0`
This will produce the same outputs as a normal fit, but without performing
any minimization, and the values will be different. I hesitate to recommend
this approach, since there is no minimisation being performed, and we want to
make sure the minimisation is also working. One option is to have one set of
tests that check the minimisation, and a separate set of tests that check the
fixed-parameter evaluation. The fixed-parameter evaluation can be done by
creating a new `.mod` file for each test case that copies the parameters from
the `.mod.out.reference` file and sets `miniter` and `maxiter` to 0 in the
top parameter block. This should produce (nearly) identical output models
as the `reference_fits/` files. To do an absolute comparison, we would instead
need to create an additional set of `reference_fits/` files that are evaluated
at the fixed parameter set from the starting values of the current `.mod` files.
I suspect this latter idea is preferred. In this case, we would need to create
a new set of `.mod` files that are copies of the existing `.mod` files (for example,
the original might be called `modelname.mod` and the new set would have names like
`modelname_fixedparam.mod`), but
with the `miniter` and `maxiter` to 0 in the top parameter block, and then run
those to generate a new set of `reference_fits/` files that are stored in a
separate directory (e.g. `reference_fits_fixed/`). The harness can then compare
the output of the fixed-parameter evaluation against these new reference files.
One point to note is that some of the `.mod` files may have randomised starting
parameters, so the fixed-parameter evaluation may not be deterministic. In that
case, we would need to alter the `.mod` file so that the random variable is replaced
with a fixed value for reproducibility.

**Q0.2 — `.covar` emission.** The `examples/` fit `.mod` files do not set
`out covar`, and none has a `.covar.reference`; the `context/fitting_examples/`
fits that *do* have `.covar.reference` presumably set `out covar`. Confirm the
harness should compare `.covar` **only** where a `.covar.reference` exists (and
that those `.mod` files already emit `.covar`).

**Response:** That's correct. We should only check the `.covar` output for those
test cases that have a corresponding `.covar.reference` file. The harness should
not expect or check for `.covar` output in cases where no reference exists, as
those fits are not intended to produce covariance matrices.

**Q0.3 — Harness location & framework.** Confirm the harness should live in the
existing top-level `tests/` directory and use `pytest` (a dev-only dependency,
per plan Q12).

**Response:** That is correct. The harness should be implemented in the top-level
`tests/` directory and utilize `pytest` as the testing framework. This allows for
easy integration with existing development workflows and CI/CD pipelines, while
keeping the test infrastructure organized and separate from the main codebase.

**Q0.4 — The `generate` example.** `examples/generate/` has no
`.mod.out.reference`; its purpose is to test the `generate` code path, and its
reference is `data/reference_fits/OI_SiII.dat` (the generated data, no `_fit`
suffix). Since Prompt 9 says to run only fit models, how should `generate` be
tested — as a special case that runs `generate_spectra.mod` and compares the
produced data to the reference, or left out of the automated suite for now?

**Response:** Good question. For the `generate` example, we should treat it as
a special case. The harness should run `generate_spectra.mod` and compare the
produced data file (`OI_SiII.dat`) against the reference in `data/reference_fits/`.
This ensures that the data generation functionality is also validated, even
though it does not involve fitting. We can include this as a separate test case
in the harness, clearly marked as a "data generation" test.
