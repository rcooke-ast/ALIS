# Prompt file for ALIS software refactoring -- STAGE 0

> **Safety net and regression harness.** Before any refactoring begins, build an
> automated regression-test harness that runs the existing ALIS on the example
> fits and compares the output against the committed golden "reference" files.
> This harness is the safety net that gates every subsequent stage: no refactor
> change may land unless the harness still passes within the agreed tolerances.
> Stage 0 must not modify any code under `alis/`; it only adds test
> infrastructure (under `tests/`).

## Tasks

> Complete in order; log each in `ALIS/claude_prompts/logs/refactor_code_stage0_log.md`
> (date + description of work done).

**0.1 — Build the test-case inventory (manifest).**
- Discover every test case: any `.mod` file that has a sibling
  `<name>.mod.out.reference`, under both `examples/` and
  `context/fitting_examples/`. Discovery is by the *presence of the reference
  file*, not by filename pattern (the fit files are `fit_spectra*.mod`,
  `*_FINAL_MODEL.mod`, etc. — not `fit_<example>.mod`).
- For each test case record: example directory, fit `.mod` file, input data
  file(s) and their paired `<datadir>/reference_fits/<dataname>_fit.dat`, whether
  a `<name>.covar.reference` exists, whether the model uses randomness
  (`random` / `sim`, e.g. `DH/Q1243p307/…_converge_newstart76.mod`), whether the
  model contains **blind parameters** (see below), and its runtime → batch. The
  runtime is read directly from the `#   Running Time (hrs)` line in the
  `.mod.out.reference` (no need to re-run to measure).
- Detect blinding per model line (two mechanisms):
  - `blind=True` / `blind=T` → the value is **hidden**, rendered as a
    `------ BLIND MODEL ------` line in `.mod.out`.
  - a non-empty `blindrange=lo,hi` → the value stays **visible** but is offset by
    a fixed, `blindseed`-seeded amount (this applies even when `blind=False`).
  Ignore `blind=False` with no `blindrange`, and commented (`#`) lines. A case is
  "blind" if any active line uses either mechanism. Known blind fits:
  `DH/J1558m0031`, `DH/Q0913p072`, `DH/J1358p0349`, `DH/J0814p5029` (all
  `blind=True`; `DH/HS0105p1619` is not blind), and `examples/blind` (which
  exercises **both** modes — an O I line with `blindrange` and a Si II line with
  `blind=True`). Any blinded case is excluded from the fixed-parameter gate
  (0.2b), since feeding the blinded `.mod.out` back either re-applies the offset
  (blindrange) or has no value to evaluate (blind=True).
- Handle multiple data directories: a fit may read data from several `../data*/`
  folders (e.g. `DH/J1358p6522` uses `data/` and `data_hrdx/`; `DH_orders` uses
  `datafit_orders/`), each with its own `reference_fits/`. Resolve each input
  data file's `_fit.dat` reference relative to that file's directory, not a fixed
  `data/`.
- Classify by that runtime into the three batches of 0.3 (< 1 min fast; 1–10 min
  medium; ≥ 10 min slow). Current distribution from the references: all
  `examples/` unit fits are **fast** except `spline/…_splineContAbs` (~3.2 min)
  and `splineabs/…` (~1.7–2.8 min) which are **medium**; `helium34/tet02OriA`
  (~0.6 min) is fast, the other helium34 fits are medium; the single-object DH /
  VMP_DLA fits and even `DH_orders` (~8.3 min) are **medium**; only
  `DH/J0814p5029` (~15.9 min) is **slow**.
- Exclude `prepfit`, `lsf_spline` (see plan Q21), and note the `generate`
  example as a special case (see Q0.4 below).
- Emit the manifest in a form the harness consumes (e.g. a small module-level
  list, or a generated fixture list) so the suite is data-driven.

**0.2 — Implement the pytest regression harness (under `tests/`).**
Each non-blind test case has two test modes; blind cases run mode (a) only.

- **(a) Minimisation test.** Run `run_alis <fit>.mod` in its `model/` directory
  (data already exists — do **not** run `generate_spectra.mod`). Compare:
  - `.mod.out` to `.mod.out.reference` by **parsing numeric fields** (best-fit
    parameters and their 1σ errors, χ², DOF); **ignore volatile header lines**
    (`Generated by ALIS on …`, `Running Time (hrs)`, `Num. of Iterations`).
    **Blinded parameters** (both modes are deterministic, so `.mod.out`
    reproduces within tolerance): `blind=True` params are **hidden** as a
    `------ BLIND MODEL ------` line — skip those and compare only χ², DOF and the
    other parameters; `blindrange` params keep a **visible** fixed-offset value —
    compare them directly like any other parameter (the large offset is identical
    in both files, so it cancels in the difference). `examples/blind` exercises
    both modes in one file (O I via `blindrange`, Si II via `blind=True`).
    **Zero printed 1σ errors**: a parameter whose reference error prints as zero
    is either tied/fixed (it carries a tie suffix, e.g. `ratrand`, `TA`; tied
    followers can jitter at print precision, so compare with a tight 1e-4
    relative fallback) or free-but-degenerate (no suffix, e.g. the unconstrained
    telluric component in `helium34/tet02OriA`, which moves arbitrarily with no
    model effect — skip it; the χ² and model-column comparisons gate any change
    that matters). Keyword-numeric tokens (e.g. `damping=11.2300905dampb`) are
    compared numerically, not as strings.
  - the produced `<dataname>_fit.dat` model column against
    `<datadir>/reference_fits/<dataname>_fit.dat`; ignore the `-9.999999999e+09`
    sentinel rows (pixels outside `fitrange`).
  - the emitted covariance file against its golden copy **only if** one exists.
    The covariance output is named by the `out covar` setting and its golden
    copy is that filename + `.reference` (naming varies:
    `J1419p0829.covar.reference`, `J0814p5029.mod.out.covar.reference`,
    `J0035m0918_all_data_covar.dat.reference`), so pair via the `out covar`
    value, not a fixed `<name>.covar.reference` pattern.
- **(b) Fixed-parameter gate (option A).** Run the `.mod.out.reference` itself (it
  is a valid `.mod` input) with `chisq miniter 0` + `chisq maxiter 0`, and
  compare the produced model column to the **existing** `reference_fits/`. This is
  fast, deterministic and minimiser-independent, so it reuses the golden files
  and needs no new references. **Skip for any blinded case** (either mode) — the
  `.mod.out` value is hidden (`blind=True`) or offset (`blindrange`), so feeding
  it back cannot reproduce the true model; those rely on mode (a) only.
  Implementation notes (Task 0.2): the gate compares **χ² (0.1%), DOF (exact)
  and the `_fit.dat` model column only** — a zero-iteration run does not
  reproduce the reference 1σ errors (e.g. shift-model errors come out 0), so
  the parameter/error blocks are compared in mode (a) only. Active `random`
  model lines are rewritten as the equivalent `variable` line (dropping
  `command=`/`start=`), because `random` would re-draw a new value on every
  run whereas `variable` keeps the best-fit value recorded in the reference.
  Where a `<name>.mod.out.reference_adjusted` sibling exists (a hand-fixed
  re-input for cases whose plain `.mod.out.reference` is not a faithful
  re-input on the current code — an output-writer round-trip bug; currently
  `examples/lsf_hst` and `examples/spline/…_splineContAbs`), the gate feeds
  that adjusted file back to ALIS but still checks χ²/DOF against the plain
  reference. The output-writer bugs themselves are queued for Stage 5
  (Task 5.4), after which the adjusted files can be removed.
  Excluded from the gate: `examples/brokenpowerlaw` (Q0.12, kept), and the
  three sharp-feature cases (`tophat`, `VMP_DLA/J0903p2628`,
  `Q1243p307_converge_newstart76`) provisionally, pending the model-column
  tolerance redefinition (Q0.15).
- **Special: the `generate` case** runs `generate_spectra.mod` and compares the
  produced data file to `data/reference_fits/<dataname>.dat` (data-generation
  test, no fit).
- Never overwrite a reference. Write generated outputs to a temp location (or
  clean them up after each test) so `.mod.out.reference`, `reference_fits/`, and
  `.covar.reference` remain pristine.

**0.3 — Batches and determinism.**
- Three pytest batches (markers), classified by per-test wall-time:
  - **fast** (< 1 min/test) — runs on every commit; the majority of tests (all
    the `examples/` unit fits **plus all fixed-parameter evaluations**, mode 0.2b,
    which are fast and deterministic even for large models).
  - **medium** (< 10 min/test) — runs nightly (e.g. the single-object DH /
    helium34 minimisation tests).
  - **slow** (on demand) — the full set, including the slowest minimisations
    (e.g. `DH_orders`, 351 spectra).
- Run **all fixed-parameter evaluations (0.2b) on every commit**, regardless of
  the case's minimisation batch.
- Handle randomised cases: `random` converges to the same best-fit but its
  `_fit.dat` varies at the ~1e-5 level run-to-run, so compare with the numeric
  tolerance (not byte-identity). Use a fixed seed / replace the random start with
  a fixed value where possible (`sim newstart` cases).

**0.4 — Tolerances.**
- **`.mod.out` best-fit parameters** (minimisation test): hard check within
  **10%** of each parameter's 1σ error; plus a softer check within **50%** of 1σ.
- **χ²:** **1%** relative for the minimisation test; **0.1%** for the
  fixed-parameter gate (0.2b).
- **`_fit.dat` model column:** minimisation test (mode a) **1e-4** relative
  (comfortably above the ~1e-5 run-to-run `random` jitter); fixed-parameter
  gate (mode b) uses the Q0.15/Q0.18 statistic instead —
  `|new − ref| / max(reference_model) < 2e-3` per pixel.
- **`.covar` elements:** **1%** relative, with an absolute floor of
  `1% · sqrt(C_ii · C_jj)` for near-zero elements.

**0.5 — Make the harness CI-ready, documented, and self-checked.**
- Add pytest configuration with the three markers (`fast` / `medium` / `slow`)
  and a short `tests/README` describing how to run each batch (e.g.
  `pytest -m fast`, `pytest -m "fast or medium"`, `pytest` for all). The GitHub
  Actions workflow itself is Stage 1.3.
- Before any `alis/` code is changed in Stage 1+, run the full harness a few
  independent times to confirm it is stable/deterministic and green on the
  current code (RJC's Q0.6 note).

**Q0.1 — Fixed-parameter evaluation.** The primary tolerance gate needs ALIS to
compute the model + χ² at a *given* parameter set without minimising. Is there a
supported way to do this in the current code (e.g. `chisq maxiter 0`, or reusing
the `generate`/`sim` machinery), or should the harness instead gate on the
end-to-end re-fit result only? Please advise the preferred mechanism.

**Response:** The current `.reference` files are generated from a full fit,
so they include the best-fit parameters and their associated χ² values. It is
possible to evaluate the model and χ² at a fixed parameter set by setting the
following parameters at the top parameter block of the `.mod` file:
`chisq miniter 0`
`chisq maxiter 0`
This will produce the same outputs as a normal fit, but without performing
any minimization, and the values will be different. I hesitate to recommend
this approach, since there is no minimisation being performed, and we want to
make sure the minimisation is also working. One option is to have one set of
tests that check the minimisation, and a separate set of tests that check the
fixed-parameter evaluation. The fixed-parameter evaluation can be done by
creating a new `.mod` file for each test case that copies the parameters from
the `.mod.out.reference` file and sets `miniter` and `maxiter` to 0 in the
top parameter block. This should produce (nearly) identical output models
as the `reference_fits/` files. To do an absolute comparison, we would instead
need to create an additional set of `reference_fits/` files that are evaluated
at the fixed parameter set from the starting values of the current `.mod` files.
I suspect this latter idea is preferred. In this case, we would need to create
a new set of `.mod` files that are copies of the existing `.mod` files (for example,
the original might be called `modelname.mod` and the new set would have names like
`modelname_fixedparam.mod`), but
with the `miniter` and `maxiter` to 0 in the top parameter block, and then run
those to generate a new set of `reference_fits/` files that are stored in a
separate directory (e.g. `reference_fits_fixed/`). The harness can then compare
the output of the fixed-parameter evaluation against these new reference files.
One point to note is that some of the `.mod` files may have randomised starting
parameters, so the fixed-parameter evaluation may not be deterministic. In that
case, we would need to alter the `.mod` file so that the random variable is replaced
with a fixed value for reproducibility.
